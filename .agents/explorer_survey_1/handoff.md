## 2. Logic Chain

### 2.1 Why the Previous Pipeline Emitted Procedural Fallbacks
1. **Observation**: When running `pytest` or `pipeline.py`, the default generation mode was `mode="auto"`.
2. **Observation**: In `generator.py` (lines 1496-1499), `check_cache()` was invoked without specifying `expected_source="meshy"`.
3. **Reasoning**: Once procedural fallback assets were generated and stored in `output/`, subsequent pipeline runs hit the local cache and returned the procedural assets as "valid cached models".
4. **Observation**: In `generator.py` line 1503, if `resolve_api_key()` was not set or an exception occurred, `generate_plant()` silently dropped into `ProceduralBotanicalGenerator`.
5. **Conclusion**: To fulfill R1 (Zero Procedural Dummy Blobs), the master generation entry point must reject procedural fallback when Meshy generation is requested, and `check_cache()` must strictly enforce `expected_source="meshy"`.

### 2.2 Why Genuine Meshy Assets Failed Existing Validation
1. **Observation**: In `tests/test_vegetation_pipeline.py`, `test_full_inspection_suite_100_percent_pass` failed specifically on `veg_tree_oak_01` with:
   ```
   Vertex count 58,853 is over budget (maximum acceptable is 45,000)
   ```
2. **Observation**: `validator.py` line 382 hardcodes:
   ```python
   within_budget = 3000 <= n_verts <= 45000
   ```
   And `catalog.py` line 122 sets `max_vertices: int = Field(default=45000, le=45000)`.
3. **Observation**: The Authoritative User Request (`## 2026-09-10T11:11:31Z`) states:
   * "ensuring every plant species exhibits authentic, distinct botanical morphology, 30k-60k polygon detail"
   * "Mesh detail target: 20,000 to 60,000 polygons per asset (quad/triangle optimized)"
   * "Average mesh detail is between 20,000 and 60,000 faces per asset"
4. **Reasoning**: The Meshy AI refine engine produces dense high-fidelity meshes between 40,000 and 60,000 polygons/vertices for complex trees like Oak (58,853 vertices, 59,487 faces).
5. **Conclusion**: The previous test suite and validator had an obsolete cap of 45,000 vertices left over from earlier low-poly requirements. It must be expanded to 65,000 (to allow up to 60k faces plus margin) to permit genuine Meshy models to pass QA.

### 2.3 Why `veg_tree_oak_01` Had Normalization & Texture Violations
1. **Observation**: `validate_asset` reported for `veg_tree_oak_01`:
   - `Ground contact base violation: Y_min = -0.950965m exceeds tolerance ±0.005m`
   - `Metric scale bounds violation: measured height 1.879m deviates from target 12.000m by 84.3%`
   - `Albedo texture lacks surface variation: std=0.0003 <= 0.02`
   - `Roughness texture lacks variation (constant flat field): std=0.0000 <= 0.01`
2. **Observation**: Inspecting the real Meshy cloud task `01a089f7-2837-7074-af0e-89c25070c634` directly via API:
   - The remote base color texture is **2048x2048** with $\mu = 0.256, \sigma = 0.0838$ (passes variation check $\sigma > 0.02$).
   - The remote roughness texture is **2048x2048** with $\mu = 0.6677, \sigma = 0.0251$ (passes variation check $\sigma > 0.01$).
3. **Reasoning**: The files in `output/broadleaf_trees/veg_tree_oak_01/` were in an un-synchronized intermediate state:
   - `veg_tree_oak_01.glb` was overwritten with raw un-normalized Meshy output ($Y_{\min} = -0.95\text{m}$, height = 1.88m, glTF Y-up) rather than the normalized asset from `post_processor.process_and_export()`.
   - The textures directory `textures/` contained residual synthetic procedural images rather than the downloaded 2K Meshy textures.
4. **Conclusion**: When Meshy models are downloaded, they must be cleanly normalized by `process_and_export()` (snapping $Z_{\min} = 0$, scaling to 12.0m, embedding and extracting the real 2K PBR texture channels).

### 2.4 Why CLI Summary Mode Failed on Windows
1. **Observation**: `test_cli_summary_mode_execution` failed with:
   ```
   UnicodeDecodeError: 'charmap' codec can't decode byte 0x9d in position 1097: character maps to <undefined>
   TypeError: argument of type 'NoneType' is not iterable
   ```
2. **Reasoning**: In `test_vegetation_pipeline.py` line 375, `subprocess.run(cmd, capture_output=True, text=True)` runs without specifying `encoding="utf-8"`. On Windows, Python subprocess text mode defaults to the legacy ANSI code page (`cp1252`), which crashes when reading UTF-8 box-drawing or botanical characters emitted by `pipeline.py --summary`.
3. **Conclusion**: The test command and CLI must explicitly pass `encoding="utf-8"` or configure `PYTHONIOENCODING=utf-8`.

## 3. Caveats

1. **Meshy Cloud API Generation Latency & Concurrency**:
   - Each Text-to-3D asset in Meshy requires two successive cloud jobs: Stage 1 Preview (~60-120 seconds) followed by Stage 2 Refine (~120-240 seconds). Generating a single plant end-to-end takes approximately 3 to 5 minutes.
   - Generating all 35 species sequentially through the live API requires ~2 hours of cloud compute. Generating in parallel (with concurrency throttled to 2-3 simultaneous tasks to avoid 429 rate limit spikes) takes ~30-45 minutes.
   - The task polling exponential backoff in `MeshyGenerator._request_with_retry` is effective, but concurrency must be bounded to prevent exhausting API limits.
2. **Species ID Naming Discrepancies**:
   - In `ORIGINAL_REQUEST.md`, R2 lists short ID examples such as `veg_trop_palm_01`, `veg_trop_monstera_01`, `veg_succ_saguaro_01`.
   - In `taxonomy_catalog.json`, the official canonical IDs are `veg_tropical_palm_01`, `veg_tropical_monstera_01`, `veg_succulent_saguaro_01`.
   - The catalog supports flexible lookup by common name, scientific name, and category, but the canonical IDs in `output/` use the full words (`veg_tropical_...`, `veg_succulent_...`). Both should be recognized as equivalent aliases.
3. **Blender Headless Preview Rendering**:
